# Week 7 D2V2 — B2H One-Page Summary

โครงการ B2H เป็นเว็บแอปสำหรับซื้อ-ขายของมือสองภายในชุมชนมหาวิทยาลัย เน้นความง่ายและปลอดภัยด้วยการยืนยันตัวตนผ่านอีเมลโดเมนมหาวิทยาลัย พร้อมฟีเจอร์โปรไฟล์ผู้ขาย รายการสินค้า รูปภาพ รีวิว รายการโปรด และรายงานการละเมิด

## Tech Stack

- Frontend: HTML5, CSS3, Vanilla JavaScript
- Backend: Node.js + Express
- Database: MySQL (ผ่าน `mysql2`)
- Auth: JWT (Bearer Token)
- File Upload: Multer (บันทึกลงโฟลเดอร์ `public/uploads`)

## Frontend Pages

- `public/index.html`: หน้าเริ่มต้น/ทางเข้า
- `public/dashboard.html`: หน้ารวมสินค้าและนำทาง
- `public/seller.html`: หน้าข้อมูลผู้ขาย + จัดการโปรไฟล์
- `public/interested.html`: รายการที่สนใจ/ติดดาว

## API Overview (หลัก ๆ)

- `POST /auth/university`: เข้าสู่ระบบด้วยอีเมลโดเมนมหาวิทยาลัย (เช่น `go.buu.ac.th`)
- `POST /register`: สมัครใช้งานด้วยอีเมล + รหัสผ่าน (ตรวจโดเมนมหาวิทยาลัย)
- `POST /login`: เข้าสู่ระบบด้วยอีเมล + รหัสผ่าน, คืน JWT
- `GET /me`: ตรวจสถานะเข้าสู่ระบบและดึงข้อมูลผู้ใช้ปัจจุบัน
- `PUT /me`: อัปเดตโปรไฟล์ผู้ใช้ (ชื่อ, รูป, ช่องทางติดต่อ)
- `POST /logout`: ออกจากระบบแบบ stateless (ฝั่ง client ลบ token)
- `GET /products`: ดึงรายการสินค้า (แสดงสถานะสินค้าเป็น badge ที่ฝั่ง client)
- `GET /favorites`: ดึงรายการโปรดของผู้ใช้ (ต้อง JWT)
- `POST /favorites/toggle`: สลับเพิ่ม/ลบสินค้าในรายการโปรด (ต้อง JWT)

## Database Schema (ย่อ)

ดูรายละเอียดเต็มใน `schema.sql`

- ตาราง `users`: จัดเก็บผู้ใช้, บทบาท (`user|admin`), สถานะ, โปรไฟล์, ช่องทางติดต่อ
- ตาราง `product`: รายการสินค้า, ผู้ขาย (`seller_id`), ราคา, หมวดหมู่, สถานะ (`available|sold|hidden`)
- ตาราง `product_images`: รูปแนบกับสินค้า (หลายรูปต่อสินค้า)
- ตาราง `reviews`: รีวิวให้กับผู้ขาย/สินค้า, คะแนน 1–5
- ตาราง `favorites`: รายการโปรดของผู้ใช้ต่อสินค้า (unique ต่อ `(user_id, product_id)`)
- ตาราง `report`: รายงานการละเมิด (สถานะ `pending|reviewed|rejected`)

## Architecture

- Express เสิร์ฟไฟล์ static จากโฟลเดอร์ `public`
- Auth ด้วย JWT: แนบ `Authorization: Bearer <token>` ไปกับ API ที่ต้องการสิทธิ์
- เชื่อมต่อฐานข้อมูลผ่าน MySQL Pool (`mysql2/promise`)
- อัปโหลดรูปด้วย Multer เก็บไฟล์ลง `public/uploads`

## Setup & Run (Windows)

1. ติดตั้ง Node.js LTS และ MySQL (เช่น XAMPP/MySQL Server)
2. สร้างฐานข้อมูลด้วยสคริปต์: เปิด MySQL แล้วรัน `schema.sql`
3. ติดตั้งแพ็กเกจ

```powershell
npm install
```

4. ตั้งค่าการเชื่อมต่อฐานข้อมูล (ดีฟอลต์ใน `server.js` คือ `root` ไม่มีรหัสผ่าน, ฐานข้อมูล `b2h`) หากแตกต่างให้ปรับค่าก่อนรัน
5. เริ่มเซิร์ฟเวอร์

```powershell
npm start
```

เปิดเบราว์เซอร์ไปที่ `http://localhost:3000` (หรือพอร์ตตามที่ตั้งค่า)

## Key Notes / ข้อสังเกต

- JWT Secret ถูกกำหนดในโค้ด (เพื่อเดโม) ควรย้ายไป `.env` ในโปรดักชัน
- ตรวจโดเมนอีเมลมหาวิทยาลัยผ่านตัวแปร `UNIVERSITY_DOMAINS` (ค่าเริ่มต้น `go.buu.ac.th`)
- ใช้ `multer` สำหรับอัปโหลดรูป เก็บไฟล์ในตัวเครื่อง ไม่ใช่ object storage
- มีการอ้างอิงแพ็กเกจ `express-session` ใน `package.json` แต่ไม่ได้ใช้ใน `server.js` (สามารถลบออกหรือใช้งานตามความเหมาะสม)

## D2 — System Design Document

### Presentation Layer (UI / API Layer)

ความหมายโดยสรุป:

- Presentation Layer เป็นจุดเข้า-ออกของระบบสำหรับผู้ใช้หรือ client (browser, mobile, 3rd‑party). ทำหน้าที่รับคำขอ แปลงเป็นรูปแบบที่ชั้น Business เข้าใจ แล้วส่งผลลัพธ์กลับในรูปแบบ HTTP/JSON/HTML ที่เหมาะสม

ความรับผิดชอบหลัก:

- รับและ parse incoming requests (headers, body, params)
- ตรวจสอบและ sanitize input (validation)
- จัดการ authentication/authorization ผ่าน middleware
- แปลงข้อมูลเข้า-ออกด้วย DTOs / mappers
- เรียก Business Layer (service) เพื่อทำงานหลักของระบบ
- จัดการข้อผิดพลาดและส่ง HTTP response ที่เหมาะสม
- ทำ logging, metrics และ rate limiting ตามนโยบาย

องค์ประกอบที่ควรมีในโปรเจค:

- Controllers / Route handlers — โฟลเดอร์ `routes/` และ `controllers/`
- Middleware — `middlewares/auth.js`, validation, error handler, logging
- Request/Response DTOs — schema สำหรับ input/output (เช่น Joi / express-validator)
- Global error handler — แปลง exception เป็น response เดียวกันทั่วระบบ
- Static file serving — Express static สำหรับ `public/`

การแยกความรับผิดชอบ:

- Controller ควรบาง (thin): ไม่เขียน business logic ตรง ๆ แต่เรียก `service`/`use-case`
- Business logic (validation เชิงธุรกิจ, การประสานหลาย repo) อยู่ที่ Business Layer
- Persistence/DB access อยู่ใน Repository/DAO

ตัวอย่างโค้ด (แนะนำแบบปรับปรุง ให้ใช้ validator และ global error handler):

```javascript
// routes/userRoutes.js
const { checkSchema } = require("express-validator");
const express = require("express");
const router = express.Router();
const userController = require("../controllers/userController");

router.post(
  "/api/v1/users",
  checkSchema({
    email: { isEmail: true, trim: true },
    password: { isLength: { options: { min: 8 } } },
    name: { optional: true, trim: true },
  }),
  userController.createUser,
);

module.exports = router;

// controllers/userController.js
exports.createUser = async (req, res, next) => {
  try {
    const { email, password, name } = req.body;
    const user = await req.container.userService.createUser(
      email,
      password,
      name,
    );
    res.status(201).json({ data: user });
  } catch (err) {
    next(err); // ส่งต่อให้ global error handler
  }
};
```

ข้อแนะนำด้านความปลอดภัยและความน่าเชื่อถือ:

- Validate และ sanitize ทุก input เพื่อป้องกัน injection
- ไม่ส่งข้อความ error ดิบจาก stacktrace ไปยัง client ใน production
- เก็บ `JWT secret` และคอนฟิกต่าง ๆ ใน `.env` / secret store
- ใช้ rate limiting & request size limits สำหรับ endpoint ที่สำคัญ

แนวปฏิบัติ (Do / Don't):

- Do: ใช้ middleware เดียวสำหรับ auth; แยก validation ลงไฟล์ schema; คืน status code ที่ถูกต้อง (201 สำหรับสร้างสำเร็จ)
- Don't: อย่าเขียน SQL หรือ business rules ใน controller; อย่า expose internal errors ให้ client โดยตรง

การเชื่อมต่อกับชั้นอื่น ๆ:

- Flow ตัวอย่าง: Client -> Router -> Auth/Validator middleware -> Controller -> Service (Business) -> Repository (Persistence) -> DB
- Controller ไม่ควรติดต่อ DB โดยตรง

สิ่งที่ควรระบุในเอกสารเพิ่มเติม (สำหรับ Presentation Layer):

- รายการ endpoints สำคัญ (method, path, request DTO, response DTO)
- รายการ middleware ที่ใช้งานและลำดับการทำงาน
- นโยบายการจัดการ error/response format (error DTO format)
- นโยบาย logging (what to log, PII handling) และ metrics ที่ต้องเก็บ
